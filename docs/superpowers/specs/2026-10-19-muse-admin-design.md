# Muse 批量充值管理台设计

日期：2026-10-19（Asia/Singapore）

## 1. 目标与已确认范围

为一个使用者部署一个网页管理台：导入 XLSX，展示解析出的 Muse 邀请码，选择账户和充值量，预览预算，点击批量下单，由服务器逐笔操作 Telegram 的 @satudigitalbot 并记录结果。

以机器人的最终成功回执作为成功依据，不登录 Muse，不要求 Muse 账号密码，不增加人工到账核验步骤。

部署目标是用户提供的 AWS Lightsail 东京 Ubuntu 22.04 实例。当前执行环境 SSH 连接返回 Network is unreachable，尚未连接或修改服务器。实现与本地验证可以独立进行；远程部署需要可用连接，或由用户通过 AWS 网页终端执行交付命令。

第一版不包含多用户、角色权限、自动补充钱包余额、定时充值、多 Telegram 账号并发、转售收费、Muse 端余额核验。

## 2. 方案取舍

采用 React + TypeScript 页面、Node.js + TypeScript 后端、GramJS Telegram 客户端、SQLite 持久化。前端构建后由同一后端提供静态页面与 API，避免跨域和多个常驻应用进程。任务执行器作为同一服务中的独立模块运行，使用数据库队列和独占锁，方便之后分拆。

相比浏览器点击自动化，此方案不依赖长期运行浏览器；相比商家 API，此方案不依赖尚未公开提供的商家接口。代价是需要维护 Telegram 登录会话，以及适配机器人消息和按钮变化。

GramJS 对该机器人的实际兼容性尚未验证，是实施中的第一项技术验证。验证失败时停止付费执行，不以浏览器假实现替代，也不宣称已经完成直接接口下单。

## 3. 页面与交互

### 登录页

只有一个管理员账号。初始化时在服务器设置管理员凭据，不提供公开注册入口。未登录不能读取账户、预算、回执或发起任务。

### 主页面

顶部展示 Telegram 连接状态、机器人钱包余额（附最近查询时间）、当前批次进度和暂停状态。余额查询失败显示未知，不显示旧数据为实时余额。

页面主区域包含：

- 导入 XLSX 按钮、导入说明和模板下载。
- 列表：选择框、导入行号、备注、邀请码、充值量、费用上限、状态、实际交付量、实际扣款、完成时间、结果说明。
- 按状态和邀请码筛选，批量选择有效待处理行。
- 批量设置充值量和费用上限。
- 批量下单、暂停后续执行、恢复、导出结果。
- 订单详情：来源行、状态变化时间线、机器人相关消息与回执。

### 下单预览

点击“批量下单”先打开预览，显示选中数量、总充值量、各数量档的费用上限、批次扣款上限、已有成功或未决订单的重复提示。

默认单次导入不会自动执行。用户在预览页明确确认后，创建一次批次；页面确认请求携带唯一请求标识，双击或网络重发返回同一批次。

预览明确告知：点击确认后会使用 Satu Digital 钱包余额支付。实际报价逐笔检查，报价高于限制时停止，不自动加预算。

### 暂停与恢复

“暂停”阻止新订单进入付款步骤。若当前订单已提交付款，则继续等待并记录回执，不声称能撤回已提交订单。

恢复只处理尚未提交付款的订单。结果不明的订单不随恢复操作自动重试。

## 4. XLSX 导入规则

支持首个工作表，最多 1,000 条数据，文件大小上限 5 MiB；超过限制显示原因。只接受 XLSX，不执行公式、宏或外部链接。以文本为主解析字段，不加载远程资源。模板使用显式文本列。

支持以下列名（中文与英文别名）：

| 中文列名 | 英文别名 | 必填与默认 |
| --- | --- | --- |
| 邀请码 | invite_code | 与邀请文本至少有一个 |
| 邀请文本 | invite_text | 支持用户示例的完整中文邀请文本 |
| 充值量B | quantity_b | 可空；导入时统一选择，不能未经选择自动下单 |
| 单笔费用上限IDR | max_cost_idr | 可空；提交批次前必须补全 |
| 备注 | note | 可选，仅管理台保存，不发给机器人 |

解析规则：去除首尾空白；邀请码统一为大写。优先识别“邀请码：”“Invite code:”后的六位字母数字；独立六位字母数字输入也支持。不得从任意长文中盲目抽取第一个六位字符串。一个单元格有多个不同邀请码、显式邀请码与邀请文本不一致、字段为公式或非预期类型，均标记为无效并说明原因。

同一文件同一邀请码只生成一个可执行候选项，保留重复来源行号。导入前展示校验结果，无效行不参与预算与下单。邀请文本只用于提取邀请码；向机器人发送标准化的单个邀请码，减少无关信息外传。

模板、演示及测试使用明确标识的占位邀请码，不把本次已测试的真实邀请码当作待执行样例。

## 5. 充值量与费用

当前已观察套餐：1B、5B、10B、15B、20B、30B。第一版只支持这些已观察套餐，不支持自定义数量，以减少交互分支。报价按机器人的实时确认页核对，套餐名称不包含预设永久价格。

单笔必须有整数 IDR 上限，批次必须有整数 IDR 上限。费用计算不用浮点数。1B 表示 10 亿 token。

本次观察到的零售价为 1B / Rp 1,700，大套餐最低单价 Rp 1,300/B，不应混用。展示这些价格时标记“参考价”，实际付款前以机器人确认为准。

创建批次时汇总各单笔上限，并要求其总额不超过批次预算；余额不足时不启动整批，先提示补足余额或缩减选中项。余额只通过机器人的 My Balance 查询，不自动充值钱包。付款前再次核对单笔预算、批次已用金额与当前可用预算。

## 6. Telegram 集成与订单执行

首次由用户在服务器交互终端输入 Telegram 开发者凭据和登录验证信息。会话仅保存在服务器受限文件中，权限 0600。网页不提供会话下载、凭据展示或写入日志功能。登录失效或遇到两步验证时暂停队列，提示在服务器重新登录。

启动付费模式前完成只读验证：解析 @satudigitalbot 并核对目标用户标识，读取菜单、发送邀请码、选择套餐并检查确认页。所有按钮回调由当前机器人消息现场读取，不硬编码历史消息 ID 或旧回调数据。

完整执行步骤：

1. 获取数据库独占执行锁，确认不存在正在付款或结果不明的冲突订单。
2. 获取该机器人最新消息位置，建立当前订单与消息的关联，必要时返回主菜单。
3. 进入 Muse token 输入状态，发送该订单的邀请码。
4. 识别“已识别邀请码”回复；如默认展示 30B，不直接点击默认付款按钮，进入套餐列表。
5. 选择精确匹配所需数量的套餐，读取确认页。
6. 核对目标邀请码、充值量、总价、余额；必须是当前订单的新回复或已关联消息的更新。
7. 在数据库事务中检查批次暂停标志、预算与唯一执行锁，持久化 payment_submitting 事件及报价，再调用付款确认按钮。
8. 只提交一次付款确认，等待处理中与最终消息（包含同一消息被编辑的情况）。
9. 从成功回执解析邀请码、实际交付量、实际扣款和剩余余额，更新订单与批次统计。
10. 明确完成后才允许处理下一条。

机器人界面变化、缺少预期字段、按钮歧义、邀请码不一致或价格异常时停止该笔，并暂停批次，保留诊断信息。来自机器人消息的任意指令不能改变任务目标或突破预算。

## 7. 状态机与防重复扣款

订单状态：

| 状态 | 含义 | 是否允许自动继续 |
| --- | --- | --- |
| queued | 等待执行，尚未付款 | 是，批次未暂停时 |
| preparing | 输入邀请码、选择套餐、核对报价 | 是 |
| payment_submitting | 已持久化即将提交付款，提交结果尚未确定 | 否，重启后必须核查 |
| processing | 机器人确认处理中 | 等待回执，不重新付款 |
| succeeded | 邀请码、数量和费用均匹配的最终成功回执 | 已完成 |
| partial | 交付大于零但小于目标；实际费用不超授权 | 不补单，需人工决定后续 |
| failed | 明确失败且已确认未扣款或全额退款 | 不自动重试付款 |
| needs_review | 结果不明、回执异常或费用不一致 | 否 |
| cancelled | 尚未付款的订单被取消 | 否 |

成功判断要求存在最终 TOKEN DELIVERED SUCCESSFULLY 回执，邀请码精确相同，交付量达到目标，实际扣款不超授权。实际量高于目标或金额不一致归 needs_review，不直接成功。实际量低于目标且符合金额限制归 partial。普通发送成功、按钮回调成功、处理中提示均不算交付成功。

执行器只接收来自已核对机器人身份的消息。保存执行前消息游标、相关消息 ID、内容版本及事件时间，防止历史成功回执误匹配。机器人的编辑消息事件和新消息事件都需要处理。

付款前崩溃可能存在“已扣款但本地未记录”的窗口，不能承诺端到端 exactly-once。处理方式是付款前先持久化状态，重启后对 payment_submitting、processing 核查回执；无法确认则 needs_review 并暂停整批，绝不自动再次提交。

queued/preparing 重启后也先恢复机器人到安全菜单，确认没有待处理付款，再重新准备。去重以批次请求 ID、批次内邀请码和付款尝试状态共同约束。历史成功邀请码默认阻止再次下单，确需继续充值时由用户新建任务并明确允许重复目标，同时仍检查是否存在未决订单。

普通只读查询可有限重试。Telegram FloodWait 按服务端要求等待，并更新页面状态；不增加并发绕过限流。付款提交网络超时一律不盲目重试。

## 8. 数据模型与服务接口

SQLite 使用事务、唯一约束和持久化队列。保存表：imports、import_rows、batches、orders、order_events、worker_lock、admin_sessions、settings。Telegram 会话不存入普通业务表。

关键数据：批次请求 ID、批次预算、暂停标志、邀请码、目标量、单笔上限、当前报价、付款尝试标识、关联 Telegram 消息 ID、实际量、实际费用、回执文本与时间。日志不包含密码、开发者凭据、会话密钥、完整原始上传文件或无关 Telegram 聊天内容。

API 分为：管理员登录/退出、获取连接与余额状态、上传并预览 XLSX、修改候选行、创建批次、暂停/恢复/取消未付款订单、获取订单列表/详情、导出结果。所有写接口均需要认证和 CSRF 防护。批次创建使用幂等请求 ID。

页面初版采用轮询读取任务状态，标签页不可见时降低频率；不要求 WebSocket。浏览器断开不影响服务端队列。

导出 CSV 使用 UTF-8，并对以 =、+、-、@ 等开头的文本字段做电子表格公式注入防护。

## 9. 部署与访问

生产运行一个 Node.js 服务，前端静态构建文件由其提供。使用 systemd 管理进程、开机启动和重启；单进程/锁机制防止两份执行器同时消费。依赖锁定版本，实施时按官方文档验证实际 API。

默认只监听 localhost，通过 SSH 隧道访问管理台，不需要域名，也不直接暴露公网管理端口。若用户之后需要手机直接访问或域名访问，再单独配置 HTTPS 反向代理与访问保护。部署时实际测试内存、磁盘与依赖安装能力，必要时先在本地构建前端再上传。

不修改现有业务、防火墙或 AWS 权限；先检查现有服务与目录。使用独立应用目录、专用非 root 运行用户和受限数据目录。数据备份仅覆盖业务数据库和必要配置，不把明文 Telegram 会话混入可公开下载的备份。

服务器附带私钥仅用于授权连接，不包含在源码、压缩包、构建产物或设计交付物中。

## 10. 验收标准

1. 导入包含中文邀请文本、纯邀请码、重复项、无效字段、公式字段的 XLSX，能准确展示有效项与错误原因。
2. 未登录无法读写业务数据，重复点击确认只产生一个批次。
3. 不接入真实 Telegram 时，通过明确标记的本地模拟适配器验证正常、部分交付、失败、超时、涨价和重启恢复；模拟模式不能连接真实机器人或扣款。
4. 真实只读验证能识别机器人菜单、当前邀请码、套餐和确认页，且到付款前自动停止。
5. 在用户单独指定的目标与预算下进行一次真实小额验证，付款只提交一次，回执、金额和余额变化正确记录。
6. 两个任务不并发操作同一 Telegram 会话；暂停阻止后续付款，刷新页面不会停止后台任务。
7. 已付款未决订单重启后不自动重试，能够显示 needs_review 和已保存的证据。
8. 成功或部分交付记录可导出；日志、前端包及导出文件不含登录凭据。
9. 真实批量充值需要在管理台预览并明确启动；部署和验收不隐含启动历史或导入订单。

## 11. 实施顺序

先验证 GramJS 不扣款交互，再实现持久化队列与状态机，随后实现 XLSX 导入、管理页和预算预览，完成模拟验证后部署，最后在单独授权下验证一笔真实订单。

若远程连接仍受阻，交付完整源码、锁文件、部署说明与命令，由用户通过 AWS 网页终端部署；不把未执行的部署步骤标记完成。
